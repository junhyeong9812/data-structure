# 28. 로프

01번 동적 배열에서 **맨 앞에 넣는 것이 O(n)** 이었습니다. 뒤를 전부 밀어야 했기 때문입니다.
자바의 `String` 도 같습니다. 불변이라 이어붙이기마다 전체를 복사합니다.

10MB 짜리 문서의 **가운데에 한 글자**를 넣어 봅시다. `String` 이면 10MB 를 복사하고
`StringBuilder` 여도 뒤쪽 5MB 를 밉니다. **타자를 한 번 칠 때마다** 그렇습니다.

로프는 문자열을 **이진 트리의 잎에 조각으로** 나눠 담습니다.
잎만 글자를 들고, 내부 노드는 왼쪽 부분트리의 길이(weight)만 압니다.

| 연산 | String | StringBuilder | Rope |
|---|---|---|---|
| 이어붙이기 | O(n+m) | O(m) 상환 | **O(1)** 뿌리 하나 만들면 끝 |
| 가운데 삽입 | O(n) | O(n) | **O(log n)** |
| 가운데 삭제 | O(n) | O(n) | **O(log n)** |
| i번째 글자 | **O(1)** | **O(1)** | O(log n) |
| 부분 문자열 | O(길이) | O(길이) | O(log n + 길이) |

**네 번째 줄이 대가입니다.** 임의 접근이 O(1) 에서 O(log n) 이 됩니다.
읽기가 압도적으로 많으면 배열이 이깁니다. **편집이 많을 때만** 로프가 이깁니다.
텍스트 에디터(Xi, CodeMirror 6, Zed), 협업 편집기, 대용량 로그 뷰어가 이것을 씁니다.

26번 영속 자료구조와 같은 발상입니다. **아무도 노드를 안 고치므로** 합칠 때 복사할 것이 없습니다.

## 특히 생각해볼 것

**1. 이어붙이기가 0 입니다.** 1000번 이어붙이면 로프 **0 글자**, 기준선 **5,005,000 글자**.
대신 깊이가 999 가 됩니다. 공짜가 아니라 외상입니다.

**2. 가운데 삽입이 이 박스의 존재 이유입니다.** 10만 자 문서 한가운데에 1000번 타자를 치면

```
StringBuilderStore   100,499,500 글자
Rope                          32 글자
```

커서를 문서 전체에 흩뿌려도 **29,376 글자**라 3421배입니다.

**3. 임의 접근은 집니다.** 10만 자 문서를 끝까지 `charAt` 으로 읽으면 노드를 **1,268,928 번**
지납니다. 조회 한 번에 12.7 노드이고 배열이었으면 1 입니다.

**4. 편집을 반복하면 기웁니다.** 앞에만 1000번 붙이면 깊이가 **999**, `rebalance()` 뒤에 **10**
입니다(06번 BST, 23번 스플레이 트리와 같은 자리). 그런데도 옮긴 글자는 **0 개**입니다.

**5. 옛 버전이 살아 있습니다.** 4096자 문서를 한 번 고치면 새 로프의 노드 259개 중 **247개가
옛 로프와 같은 객체**입니다. 1000 버전을 다 들고 있어도 옮긴 글자는 12,502 개(기준선 4,595,500).

**6. 잎 크기가 절충입니다.** 4096자 문서를 짓고 200곳을 고쳐 봤습니다.

| leafMax | 노드 수 | 4096번 조회의 방문 노드 | 편집 200번이 옮긴 글자 |
|---|---|---|---|
| 1 | 8191 | 53,248 | **0** |
| 4 | 2047 | 45,056 | 536 |
| 32 | 255 | 32,768 | 4,902 |
| 256 | 31 | 20,480 | 17,834 |
| 4096 | 1 | 4,096 | 48,931 |

**작으면 노드가 폭발하고 크면 복사가 폭발합니다.**
실제 에디터가 이 표보다 훨씬 큰 값을 쓰는 것은 캐시 때문입니다.

**7. 구조 공유가 비교를 건너뛰게 합니다.** 같은 문서에서 갈라진 두 버전은 4096 글자 중
**33 글자만 비교**하면 됩니다(나이브 4097). 따로 만든 두 로프에는 공유가 없어 그때는 나이브와
똑같습니다. **이 최적화는 편집 이력이 있을 때만 듭니다.**

## 한계 (고칠 수 없는 성질)

**1. 작은 문서에서는 집니다.** 10글자 문서에서 세 글자를 지우면 로프는 8글자를 옮기고
기준선은 7글자만 옮깁니다. 트리를 유지하는 값이 이득보다 큰 구간이 있습니다.

**2. `charAt` 은 어떤 방법으로도 O(1) 이 안 됩니다.** 잎을 키우면 조회는 싸지지만 편집이 비싸집니다.

**3. 재귀가 깊이에 걸립니다.** `toString` 과 잎 모으기가 재귀라 이 기계 기본 스택에서
**깊이 19,628 은 살고 19,726 에서 `StackOverflowError`** 입니다(앞에만 2만 번 붙이면 닿습니다).
`charAt` 은 반복문이라 78,903 에서도 삽니다. 실무 구현이 자동 `rebalance` 를 거는 이유입니다.

**4. 잎이 잘게 부서지는 것은 못 되돌립니다.** `rebalance` 는 모양만 고치고 잎은 그대로 둡니다.
작은 잎을 합치려면 복사 0 이 깨집니다. 실제 구현은 그 값을 내고 합칩니다.

**5. 테스트가 못 잡는 변종이 둘 있습니다.** `splitNode` 의 `index == node.weight` 지름길을
지워도, `appendRange` 의 가지치기를 `Math.min` 으로 눌러 써도 **110개가 다 통과합니다.**
둘 다 노드 객체까지 같은 동치 변환이었습니다(훑어 자르는 O(n) 구현은 성능 테스트가 잡습니다).
11번 `h2 == 0`, 16번 뿌리 색, 18번 `nextSetBit`, 22번 패딩, 23번 `SplayTreeSet.add`,
24번 블룸 방어에 이어 일곱 번째입니다.

**6. 필드 이름이 계약입니다.** `RopeStructureTest` 가 `root`, `leafMax`, `charAtVisits` 와 `Node` 의 필드를 리플렉션으로 봅니다.
