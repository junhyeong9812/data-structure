# 28. 로프

01번 동적 배열에서 **맨 앞에 넣는 것이 O(n)** 이었습니다. 뒤를 전부 밀어야 했기 때문입니다.
자바의 `String` 도 같습니다. 불변이라 이어붙이기마다 전체를 복사합니다.

10MB 짜리 문서의 **가운데에 한 글자**를 넣어 봅시다. `String` 이면 10MB 를 복사하고
`StringBuilder` 여도 뒤쪽 5MB 를 밉니다. **타자를 한 번 칠 때마다** 그렇습니다.

로프는 문자열을 **이진 트리의 잎에 조각으로** 나눠 담습니다.

```
잎         실제 문자열 조각을 들고 있다
내부 노드   글자가 하나도 없다. 왼쪽 부분트리의 전체 길이(weight)만 안다
```

| 연산 | String | StringBuilder | Rope |
|---|---|---|---|
| 이어붙이기 | O(n+m) | O(m) 상환 | **O(1)** 뿌리 하나 만들면 끝 |
| 가운데 삽입 | O(n) | O(n) | **O(log n)** |
| 가운데 삭제 | O(n) | O(n) | **O(log n)** |
| i번째 글자 | **O(1)** | **O(1)** | O(log n) |
| 부분 문자열 | O(길이) | O(길이) | O(log n + 길이) |

**네 번째 줄이 대가입니다.** 임의 접근이 O(1) 에서 O(log n) 이 됩니다.
읽기가 압도적으로 많으면 배열이 이깁니다. **편집이 많을 때만** 로프가 이깁니다.
텍스트 에디터(Xi, CodeMirror 6, Zed), 협업 편집기, 대용량 로그 뷰어가 이것을 씁니다.

## 불변이라서 이어붙이기가 공짜입니다

26번 영속 자료구조와 같은 발상입니다. 아무도 노드를 안 고치므로 두 로프를 합칠 때
**양쪽을 그대로 자식으로 삼아도** 안전합니다. 고칠 수 있는 자료구조였다면 한쪽을 복사해야 했습니다.
그리고 삽입과 삭제가 전부 `split` 과 `concat` 으로 만들어집니다. `insert` 는 쪼개고 둘 붙이기,
`delete` 는 두 번 쪼개고 가운데 버리기입니다.

## 특히 생각해볼 것

**1. 이어붙이기가 0 인지 숫자로 확인하세요.** 1000번 이어붙이면 로프는 **0 글자**, 기준선은
**5,005,000 글자**를 옮깁니다. 대신 로프의 깊이가 999 가 됩니다. 공짜가 아니라 외상입니다.

**2. 가운데 삽입이 이 박스의 존재 이유입니다.** 10만 자 문서 한가운데에 1000번 타자를 치면

```
StringBuilderStore   100,499,500 글자
Rope                          32 글자
```

로프의 32 는 잎 하나를 처음 한 번 쪼갠 값입니다. 그 뒤로는 커서 자리가 이미 잎 경계라
쪼갤 것이 없습니다. 커서를 문서 전체에 흩뿌리면 **29,376 글자**가 되는데 그래도 3421배입니다.

**3. 임의 접근은 집니다.** 10만 자 문서를 끝까지 `charAt` 으로 읽으면 노드를 **1,268,928 번**
지납니다. 조회 한 번에 12.7 노드이고 배열이었으면 1 입니다. 읽기만 하는 코드에는 그냥 손해입니다.

**4. 편집을 반복하면 기웁니다.** 앞에만 1000번 붙이면 깊이가 **999**, `rebalance()` 뒤에 **10**
입니다(06번 BST, 23번 스플레이 트리와 같은 이야기). `rebalance` 는 **잎 객체를 그대로 다시 매답니다.**
글자를 한 개도 안 옮기고 1000개 잎이 전부 같은 객체입니다. 불변이 아니면 이렇게 못 합니다.

**5. 옛 버전이 살아 있습니다.** 편집해도 앞 로프가 그대로입니다. 4096자 문서를 한 번 고치면
새 로프의 노드 259개 중 **247개가 옛 로프와 같은 객체**이고 새로 만든 것은 12개입니다.
1000 버전을 전부 들고 있어도 옮긴 글자가 12,502 개인데 기준선은 4,595,500 개입니다(367배).

**6. 잎 크기가 절충입니다.** 4096자 문서를 짓고 200곳을 고쳐 봤습니다.

| leafMax | 노드 수 | 4096번 조회의 방문 노드 | 편집 200번이 옮긴 글자 |
|---|---|---|---|
| 1 | 8191 | 53,248 | **0** |
| 4 | 2047 | 45,056 | 536 |
| 32 | 255 | 32,768 | 4,902 |
| 256 | 31 | 20,480 | 17,834 |
| 4096 | 1 | 4,096 | 48,931 |

**작으면 노드가 폭발하고 크면 복사가 폭발합니다.** 잎 하나에 문서를 다 담으면 배열과 같아집니다.
실제 에디터가 이 표보다 훨씬 큰 값(수백에서 수천 바이트)을 쓰는 것은 캐시 한 줄을 읽는 것이
노드를 따라가는 것보다 훨씬 싸기 때문입니다.

**7. 구조 공유가 비교를 건너뛰게 합니다.** `longestCommonPrefixLength` 에서 두 부분트리의
**참조가 같으면 내용도 같습니다.** 불변이라 성립하는 추론입니다. 같은 문서에서 갈라진 두 버전은
앞 4096 글자 중 **33 글자만 비교**하면 답이 나옵니다(나이브는 4097). 다만 따로 만든 두 로프에는
공유가 없어서 그때는 나이브와 똑같습니다. **이 최적화는 편집 이력이 있을 때만 듭니다.**

## 한계 (고칠 수 없는 성질)

**1. 작은 문서에서는 집니다.** 10글자 문서에서 세 글자를 지우면 로프는 잎 둘을 쪼개느라
8글자를 옮기고 기준선은 7글자만 옮깁니다. 트리를 유지하는 값이 이득보다 큰 구간이 있습니다.

**2. `charAt` 은 어떤 방법으로도 O(1) 이 안 됩니다.** 잎에 도착해야 글자가 있어서입니다.
잎을 키우면 조회는 싸지지만 편집이 비싸집니다(위 표).

**3. 재귀가 깊이에 걸립니다.** `toString` 과 잎 모으기가 재귀라 이 기계 기본 스택에서
**깊이 19,628 은 살고 19,726 에서 `StackOverflowError`** 입니다(앞에만 2만 번 붙이면 닿습니다).
`charAt` 은 반복문이라 깊이 78,903 에서도 삽니다. 23번 스플레이 트리와 같은 자리이고,
실무 구현이 자동 `rebalance` 를 거는 이유입니다.

**4. 잎이 잘게 부서지는 것은 못 되돌립니다.** `rebalance` 는 모양만 고치고 잎은 그대로 둡니다.
작은 잎을 합치려면 글자를 옮겨야 하고 그러면 복사 0 이 깨집니다. 실제 구현은 그 값을 내고 합칩니다.

**5. 테스트가 못 잡는 변종이 둘 있습니다.** `splitNode` 의 `index == node.weight` 지름길을
지우고 `index >= node.weight` 로 오른쪽에 맡겨도 **110개가 다 통과합니다.** `concatNodes` 가
빈 쪽을 걸러내므로 결과도 복사량도 노드 객체까지 같은 동치 변환입니다. `appendRange` 의 가지치기도
`Math.min` 으로 구간을 눌러 쓰면 같은 자리에서 멈춰 티가 안 납니다(통째로 훑어 자르는 O(n)
구현은 성능 테스트가 잡습니다). 11번 `h2 == 0`, 16번 뿌리 색, 18번 `nextSetBit`, 22번 패딩,
23번 `SplayTreeSet.add`, 24번 블룸 방어에 이어 일곱 번째입니다.

**6. 필드 이름이 계약입니다.** `RopeStructureTest` 가 리플렉션으로 `root`, `leafMax`,
`charAtVisits` 와 `Node` 의 필드를 봅니다. 계측 전용인 `charAtVisits` 만 `final` 이 아닙니다.
