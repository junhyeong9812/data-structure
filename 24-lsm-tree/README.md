# 24. LSM 트리

15번 B+트리는 **읽기**에 최적화되어 있었습니다. 높이가 4면 디스크를 4번 읽고 끝납니다.
그런데 **쓰기**를 보세요. 키 하나를 넣으려면 그 키가 들어갈 잎을 찾아가 **그 자리에** 써야 합니다.
디스크에서 그것은 **임의 쓰기(random write)**입니다.

디스크는 순차 쓰기가 임의 쓰기보다 수십에서 수백 배 빠릅니다. SSD도 그렇습니다.
읽고 쓰는 단위(페이지)보다 지우는 단위(블록)가 훨씬 커서, 제자리를 고치려면 블록을 통째로 옮겨 써야 합니다.

그래서 **쓰기가 압도적으로 많은 워크로드**(로그, 시계열, 이벤트 스트림)에서는 B+트리가 무너집니다.

## 거래를 뒤집습니다

```
쓰기   메모리의 정렬 구조(memtable)에 넣습니다. 디스크를 안 건드립니다
       차면 통째로 순차로 쏟습니다(SSTable). 절대 제자리를 안 고칩니다
읽기   memtable부터 최신 SSTable까지 차례로 뒤집니다. 여러 번 봐야 합니다
삭제   지우지 않습니다. "지웠다"는 표시(tombstone)를 새로 씁니다
정리   쌓인 SSTable을 주기적으로 합칩니다(compaction)
```

| | B+트리 (15) | LSM 트리 (24) |
|---|---|---|
| 쓰기 | 임의 쓰기 | **순차 쓰기만** |
| 읽기 | O(log n) 한 번 | **SSTable 수만큼** |
| 삭제 | 즉시 | tombstone, 나중에 정리 |
| 공간 증폭 | 낮다 | **높다** (같은 키의 옛 버전들) |
| 쓰는 곳 | MySQL, PostgreSQL | **RocksDB, 카산드라, LevelDB, HBase** |

**공짜가 없습니다.** 쓰기를 순차로 만든 대가를 읽기와 공간이 내고, 그 대가를 줄이려고 블룸 필터(11번)와 compaction이 붙습니다.

## 시그니처가 이미 설계를 말합니다

15번 `put`은 옛 값을 반환했습니다. 여기 `put`은 `void`입니다. **옛 값을 돌려주려면 먼저 읽어야 하고,
읽지 않는 것이 이 구조의 전부이기 때문입니다.** RocksDB도 카산드라도 Put은 값을 안 돌려줍니다.

## 특히 생각해볼 것

**1. 읽기 증폭은 숫자로 봐야 실감납니다.** SSTable이 10장이면 **없는 키 하나를 확인하는 데 10번**
뒤집니다. 있는 키는 그 키가 있는 층까지만 내려가므로, 1000개를 전부 조회하면 정확히 5500번입니다.
15번 B+트리는 어느 쪽이든 4번이었습니다.

**2. 블룸 필터가 그 비용의 대부분을 지웁니다.** 없는 키 1만 개를 조회하면
**10만 번이 955번이 됩니다(104배).** 955는 오탐(1% 목표)의 수이고, 해시가 결정적이라 정확히 재현됩니다.

그런데 **있는 키에는 별로 못 줄입니다.** 5500이 1051이 되는데, 그 1000번은 어차피 진짜 읽어야 하는
몫입니다. 블룸이 아는 것은 "없다" 한쪽뿐이라는 비대칭이 여기서 그대로 드러납니다.

**3. 증폭이 셋이고 서로 밉니다.** 같은 키를 100번 갱신하면 저장된 엔트리가 100개(공간 증폭 100배),
`compact()`하면 1개가 됩니다. 그런데 100개마다 합치면 순차 쓰기가 14,780바이트에서 **95,080바이트로
6.4배**가 됩니다(쓰기 증폭). 자주 합치면 쓰기가 늡니다. **셋을 동시에 줄일 수는 없습니다.**

**4. 부분 compaction에서 tombstone을 지우면 삭제가 되살아납니다.** **합친 직후에는 아무 증상이 없고**,
아래층이 살아 있는 동안만 조용히 틀립니다. `TombstoneTest.Resurrection`이 그 장면을 재현합니다.

**5. "제자리를 안 고친다"를 구조 테스트가 못 박습니다.** `SSTable`의 필드가 전부 `final`이고
클래스도 `final`이며 `set`, `add`, `put`으로 시작하는 메서드가 없다는 것을 리플렉션으로 봅니다.
**필드 이름이 계약입니다** - `keys`, `values`, `bytes`, `bloom`을 바꾸면 이 테스트가 깨집니다.

**6. 층 순서를 뒤집으면 컴파일도 되고 예외도 안 나고 옛 값이 나옵니다.** `get`, `mergedLive`,
`Compactor` 셋 중 하나만 뒤집어도 TreeMap 대조가 잡습니다(2만 스텝 x 임계치 4종).

## 한계 (고칠 수 없는 성질)

**1. 조회 비용이 층수에 비례합니다.** 블룸 필터는 **없는 키**만 싸게 만듭니다.
있는 키를 찾는 최소 비용 1회는 어떤 필터로도 못 없앱니다.

**2. 지운 데이터가 즉시 안 없어집니다.** `delete`는 공간을 늘립니다. "삭제했는데 디스크가 안 줄어든다"는
카산드라 운영의 고전적인 질문이 이것이고, 답은 "compaction이 돌 때까지 기다려라"입니다.

**3. `size()`가 O(전체)입니다.** 산 키를 세려면 모든 층을 병합해야 합니다.
실제 LSM 저장소들이 정확한 count API를 잘 안 주는 이유입니다.

**4. 잡히지 않는 변종이 하나 있습니다.** 블룸 필터의 `h2 == 0` 방어를 지워도 **72개가 다 통과합니다**
(11번과 같은 이유). 지우지 않고 남기되 **테스트가 못 잡는다는 것을 알고** 남깁니다.
(16번 뿌리 색, 18번 `nextSetBit`, 22번 패딩 `Arrays.fill`에 이어 다섯 번째입니다.)

`SSTable` 생성자의 정렬 전제 검사도 **정상 경로에서는 도달할 수 없습니다.** 다만 이쪽은 생성자가
공개 API라 테스트가 직접 어긋난 목록을 넣어 봅니다. 지우면 2개가 무너집니다.

**5. 실제 LSM과 다른 점 셋.** 여기는 층이 평평합니다(leveled compaction 없음),
WAL이 없어 memtable이 날아가면 그대로 잃고, memtable에 TreeMap을 씁니다.
실무는 12번 스킵 리스트를 쓰는데 락 없는 동시 삽입이 되기 때문입니다.
