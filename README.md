# 자료구조 문제집

**따라치면서 흡수하는** 구조입니다. 읽기만 해서는 남지 않는다는 판단에서 출발했습니다.

```
테스트를 따라친다  ->  계약을 안다
스켈레톤을 채운다  ->  구현을 안다
문제를 푼다        ->  왜 이 자료구조인지 안다
```

---

## 왜 구조를 바꿨나

이전 구조(`_archive/`)는 문제당 POP/OOP 2벌 + `SOLUTION.md` + `USEFUL.md` + `docs/` 였습니다.
결과가 이랬습니다.

| | 줄수 |
|---|---|
| 구현 | 6,513 (01~08만 실구현, **09~30 22개는 빈 스텁**) |
| 테스트 | 27,291 |
| 문서 | 46,682 |

**문서와 테스트가 구현의 11배였고, 진도는 8번에서 멈췄습니다.**
설계와 문서를 먼저 완성하고 구현을 나중에 하는 구조였는데 그 나중이 오지 않았습니다.

그래서 세 가지를 바꿨습니다.

- **POP/OOP 2벌을 버렸습니다.** 같은 문제를 두 번 풀면 두 번째는 첫 번째의 기계적 번역이 됩니다.
  대립축이 필요하면 **구현 전략**(배열 기반 vs 연결 기반, 체이닝 vs 개방주소)으로 잡습니다.
- **문서에 상한을 뒀습니다.** 문제당 README **100줄, 예외 없음.** `SOLUTION.md` 류는 만들지 않습니다.
  이전 구조를 무너뜨린 것이 문서였으므로 여기는 타협하지 않습니다.
- **테스트는 목표치만 둡니다.** 파일당 250줄 안팎을 지향하되, **계약을 지우면서까지 맞추지 않습니다.**
  (파일럿에서 실제로 그 실수를 했습니다. 250줄을 맞추려고 계약 테스트를 삭제했다가 되돌렸습니다.
  캡을 맞추려 계약을 지우는 순간 캡이 목적을 배반합니다.)

기존 자산은 `_archive/` 에 그대로 있습니다. 지우지 않았습니다.

## 문제 하나의 구성

```
NN-name/
  README.md                     개념, 복잡도, 생각해볼 것 (100줄 이내)
  src/main/java/.../
    Xxx.java                    스켈레톤 - 자명한 건 채워져 있고 핵심만 TODO
    XxxProblems.java            스켈레톤 - 이 자료구조로 푸는 응용 문제
  src/test/java/.../
    XxxTest.java                계약을 드러내는 테스트 (따라치는 대상)
    XxxProblemsTest.java
  impl/                         [참고용, 컴파일 대상 아님]
    Xxx.java
    XxxProblems.java
```

**스켈레톤에서 전부 비우지 않는 이유**가 있습니다. 전부 비우면 따라치기가 아니라 백지 구현이 되고,
전부 채우면 필사가 됩니다. 자명한 것(`size`, `isEmpty`, 범위 검사)은 채워두고
**생각이 필요한 것만** 비웁니다.

**`impl/` 을 보는 것은 괜찮습니다.** 다만 보고 나면 다시 스켈레톤으로 돌아가 직접 치세요.
눈으로 읽은 것은 손이 기억하지 않습니다.

### 구현체가 여러 개인 자료구조

스택(배열 기반 vs 연결 기반), 해시맵(체이닝 vs 개방주소)처럼 전략이 갈리는 주제는 이렇게 둡니다.

```
03-stack/
  src/main/java/.../
    Stack.java              인터페이스. TODO 없음 - 계약은 주어지는 것이다
    ArrayStack.java         스켈레톤
    LinkedStack.java        스켈레톤
  src/test/java/.../
    StackContractTest.java  abstract. 계약 테스트를 한 번만 쓴다
    ArrayStackTest.java     extends StackContractTest, create() 만 override (3줄)
    LinkedStackTest.java    같음
  impl/                     src/main 과 같은 패키지 구조를 그대로 미러링한다
```

계약 테스트를 추상 클래스로 두면 따라칠 분량이 늘지 않으면서 실패가 어느 구현인지 클래스 이름으로 바로 드러납니다.
`XxxProblems` 는 **인터페이스 대상**으로 작성해 두 구현 모두에서 돌게 합니다.
그래야 "왜 자료구조가 여러 개인가"가 실제로 드러납니다.

### 테스트가 내부를 들여다보는 경우

"지운 자리의 참조를 끊었는가" 같은 것은 공개 API 로 관측할 수 없습니다.
그런 항목은 테스트가 리플렉션으로 내부 필드를 봅니다. **그 경우 필드 이름은 계약의 일부**이고,
문제 README 에 그 사실을 적습니다.

## 실행

```bash
cd ~/project/myway/data-structure

./run.sh 01        # 01번만
./run.sh           # 전체 (통과/실패 요약)
./run.sh --check   # impl 이 실제로 통과하는지 확인
```

`--check` 는 **`src/main` 을 건드리지 않습니다.** `impl/` 이 별도 Gradle 소스셋이라 그대로 컴파일해
같은 테스트를 돌립니다. 파일을 덮어썼다 되돌리는 방식이 아니므로 중간에 끊겨도 작업 중인 코드가 안전합니다.
덤으로 스켈레톤 시그니처를 바꾸면 `impl/` 이 컴파일에서 걸립니다.

회귀 감지가 필요하면 `-Pstrict` 를 붙이세요. 평소에는 실패해도 전체 목록을 보여주려고 exit 0 입니다.

```bash
./gradlew :01-dynamic-array:test -Pstrict
```

`gradle.properties` 에 JDK 21 경로를 박아뒀으므로 **`export JAVA_HOME` 은 필요 없습니다.**
`./gradlew :01-dynamic-array:test` 로 직접 돌려도 됩니다.

처음 돌리면 전부 실패합니다. 그게 정상입니다.
