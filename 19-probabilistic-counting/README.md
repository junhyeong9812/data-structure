# 19. 확률적 집계 (Count-Min 스케치, HyperLogLog)

11번 블룸 필터는 **"있나 없나"** 하나만 답했습니다. 여기서 두 걸음 더 갑니다.

```
"몇 번 나왔나"             ->  Count-Min 스케치
"서로 다른 것이 몇 개인가"  ->  HyperLogLog
```

정확히 답하려면 둘 다 **원소 종류 수에 비례하는 메모리**가 필요합니다. 1억 종류면 수 GB입니다.
그런데 대부분의 스트림에서 원소의 대다수는 한두 번 나오고 끝납니다.
**궁금한 것은 많이 나온 소수인데 메모리는 안 궁금한 다수가 먹습니다.**

## 11번의 비대칭이 여기서 다시 나옵니다

두 구조 모두 칸 수를 **미리 고정**합니다. 그리고 블룸 필터의 쓸모였던
"없다가 확실하다"는 **한쪽 방향**이 여기서는 이 모양으로 나옵니다.

```
추정치 >= 실제                        예외 없음. 절대 과소평가하지 않는다
추정치 <= 실제 + epsilon x 전체개수   확률 (1 - delta) 로
```

상한을 알면 판단할 수 있습니다. **한 방향으로만 틀리는 것이 쓸모의 전부입니다.**

| | 정확 (HashMap/HashSet) | 스케치 |
|---|---|---|
| 100만 종류 빈도 | 64,000,000 바이트 | **108,760 바이트** (588배) |
| 100만 개 카디널리티 | 48,000,000 바이트 | **16,384 바이트** (2929배) |
| 오차 | 없다 | 위로만 / 약 0.8% |
| 원소를 되찾기 | 된다 | **안 된다** |
| 합집합 | 둘을 다 훑는다 | **레지스터 max 만. O(m)** |
| 교집합 | 된다 | **안 된다** |

배수는 전부 실측입니다. 테스트가 이 숫자를 박아두고 있습니다.

## 특히 생각해볼 것

**1. 왜 최소인가.** 칸은 남의 계수까지 받아 부풀어 있고 절대 깎이지 않습니다. 모든 행이 실제
이상이니 가장 덜 부푼 행이 가장 정확합니다. 평균이나 최대를 써도 **과소평가는 안 합니다.**

**2. 행을 늘려도 오차 크기는 안 줄어듭니다.** 줄어드는 것은 "한계를 넘을 확률"입니다. `w`가
오차를, `d`가 신뢰도를 정합니다. 실측으로 행 1개 대 7개의 평균 초과분이 400 대 314입니다.

**3. Count-Min 스케치는 heavy hitter 에만 쓸모가 있습니다.** 오차 `epsilon x 전체개수`는
**절대량**이라 전체 90만 개면 900입니다. 빈도 10만짜리에는 0.14%지만 빈도 1~3짜리에는
통째로 잡음이고, 실측으로 드문 원소의 상대 오차가 **174배**까지 갑니다.

**4. HyperLogLog는 작은 카디널리티에서 무너집니다.** 조화평균만 쓰면 레지스터 16384개 중 10개만
켜져 있을 때 분모에 `2^0`이 16374번 더해져 **분모가 카디널리티와 무관해집니다.** 실측으로 10개를
**11822개**로 셉니다(빈 것도 11817개). 그래서 linear counting 보정이 있습니다.

**5. merge 가 이 문제의 핵심입니다.** 레지스터별 max 한 줄인데 결과가 한 번에 넣은 것과
**비슷한 정도가 아니라 바이트 단위로 같습니다.** max 가 결합법칙과 교환법칙을 지키니까요.
서버 100대가 각자 16KB씩만 보내면 원본을 하나도 안 옮기고 전체를 압니다(레디스 PFMERGE).

**6. 그런데 합집합은 되고 교집합은 안 됩니다.** `|A n B| = |A| + |B| - |A u B|`는 산술적으로
맞지만 **오차가 큰 수 셋의 뺄셈**입니다. 10만짜리 두 집합의 0.8% 오차는 800인데 답이 50이면
의미가 없습니다. 실측: 겹침 5만이면 오차 0.9%, 겹침 500이면 97%, 겹침 50이면 **1540%**.

**7. 무작위는 반드시 주입받게 만듭니다**(12번과 같은 이유). 덕분에 11번에서 **못 잡았던
방어선을 여기서 잡습니다.** `h2 == 0`이면 모든 행이 같은 칸을 보는데, 11번은 입력이 int
42억 가지뿐이라 그런 값이 없었습니다. 여기서는 `mix64`를 거꾸로 풀어 그런 (원소, seed) 짝을
만들어 찔러봅니다. **씨앗 주입만으로 테스트 가능해진 코드입니다.**

## 한계 (변종 25개를 돌려 확인한 것)

21개는 잡혔습니다. **넷은 안 잡혔습니다.**

| 안 잡힌 변종 | 판정 |
|---|---|
| 랭크 상한 `Math.min(rank, 64-p+1)` 제거 | 도달 불가능. `mix64`의 하위 50비트가 전부 0이어야 하는데 int 입력으로는 닿지 않습니다 |
| linear counting 의 `zeros > 0` 검사 제거 | 도달 불가능. 레지스터가 다 차면 `raw`가 이미 `2.5m`을 넘어 앞 조건이 막습니다 |
| 레지스터 번호를 상위 대신 **하위** p비트로 | **동치입니다.** `mix64`가 잘 섞어 어느 쪽이든 고르게 퍼집니다. 관례가 상위 비트인 것은 랭크가 쓰는 비트와 안 겹치게 하려는 것뿐입니다 |
| 샤드별 스케치 없이 한 통에 바로 넣기 | **답이 완전히 같습니다.** 달라지는 것은 네트워크 바이트인데 한 프로세스 안의 테스트는 그것을 못 봅니다 |

마지막 줄이 가장 정직해야 할 곳입니다. **분산 집계라는 존재 이유 자체를 테스트가
지켜주지 못합니다.** 11번 `h2 == 0`, 18번 꼬리 비트 검사에 이어 같은 발견이 또 나왔습니다.

고칠 수 없는 것은 셋입니다. 원소를 **되찾을 수 없고**(칸이 누구 것인지 모릅니다), 드문 원소의
빈도는 **못 쓰고**, 교집합은 **하면 안 됩니다.**
