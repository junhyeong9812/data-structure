# 35. 메모리 할당자

01번부터 34번까지 필요할 때마다 `new` 를 썼습니다. **그 `new` 가 하는 일**이 이것입니다.

고정된 공간에서 자리를 떼어주고 돌려받습니다. 코드는 짧습니다.
어려운 것은 **어디를 떼어줄지**이고, 그 선택의 결과는 한참 뒤에 나타납니다.

## 남은 공간이 512인데 17을 못 줍니다

16바이트 64개로 1024를 꽉 채우고 한 칸 걸러 돌려주면, 남은 총량 512에
가장 큰 덩어리 16, 덩어리 수 32가 됩니다. `allocate(17)` 이 실패합니다.

절반이 비어 있는데 못 줍니다. **외부 단편화**입니다. `freeBytes` 만 보면 여유로워 보이고,
`largestFreeBlock` 을 같이 봐야 드러납니다.

## 다섯 구현

| | 고르는 규칙 | 회수 | 외부 단편화 | 내부 단편화 |
|---|---|---|---|---|
| `BumpAllocator` | 밀어올린다 | **안 한다** | **없다** | 없다 |
| `FirstFitAllocator` | 맞는 것 중 제일 앞 | 한다 | 있다 | 없다 |
| `BestFitAllocator` | 맞는 것 중 제일 작은 것 | 한다 | 있다 | 없다 |
| `WorstFitAllocator` | 맞는 것 중 제일 큰 것 | 한다 | 있다 | 없다 |
| `BuddyAllocator` | 2의 거듭제곱으로 쪼갠다 | 한다 | 적다 | **있다** |

**계약 테스트 117개를 다섯이 다 통과합니다.** 갈리는 것은 한참 쓰고 난 뒤의 모양입니다.

## 그럴듯한 이유가 양쪽에 다 있습니다

best fit 은 "큰 자리를 아껴두자"이고 worst fit 은 "남는 조각을 크게 만들자"입니다.
둘 다 말이 됩니다. 요청 300개를 같은 순서로 넣어보면:

| | 실패 | 남은 덩어리 | 훑은 횟수 |
|---|---|---|---|
| first fit | **169** | 7 | **1,467** |
| best fit | 170 | 7 | 1,886 |
| worst fit | 178 | 9 | 2,519 |

**제일 단순한 것이 이겼습니다.** best fit의 "큰 자리를 아낀다"는 이 요청 열에서 안 통했고,
훑는 비용만 더 들었습니다. **재기 전에는 어느 쪽이 맞는지 알 수 없습니다.**

## 한쪽을 없애면 다른 쪽이 생깁니다

버디는 2의 거듭제곱으로만 쪼개서 외부 단편화를 줄입니다. 대신 33을 달라면 64를 줍니다.
33바이트를 **16번** 떼어주면 1024가 꽉 차는데, 실제로 쓰는 것은 528이고 **496이 갇힙니다.**
`freeBytes` 는 0이라 "꽉 찼다"로 보입니다. 같은 요청을 first fit 은 **31번** 받습니다.

**갇힌 496바이트는 어떤 자에도 안 잡힙니다.** 쓰이지도 않고 돌려주지도 못합니다.

## 특히 생각해볼 것

**1. 합치기를 안 해도 계약 테스트는 거의 다 통과합니다.** 남은 총량이 맞기 때문입니다.
잘게 부서진 것은 **가장 큰 덩어리를 재야만** 드러납니다.
"자를 하나만 두면 안 되는" 자리이고, 이 박스가 자를 여섯 개 두는 이유입니다.

**2. 무엇을 정렬해 두느냐가 무엇을 할 수 있는지를 정합니다.** 빈 자리 목록을 주소순으로 들면
고르기가 느려지고 **합치기가 가능해집니다.** 크기순으로 들면 반대입니다.

**3. 버디는 짝의 주소를 계산으로 구합니다.** `주소 XOR 크기` 한 줄입니다.
18번 비트셋의 "위치 계산을 산술로 바꾸기"가 여기서 **자료구조의 성질**이 됩니다.

**4. 버디는 붙어 있어도 짝이 아니면 못 합칩니다.** `[256,512)` 와 `[512,768)` 은
인접한데 512짜리로 못 만듭니다. 빈 자리 목록 방식은 같은 상황에서 성공합니다.
그 제약이 O(1) 합치기의 값입니다.

**5. 버디가 늘 이기는 것이 아닙니다.** 요청이 이미 2의 거듭제곱이면 올림이 안 일어나고,
그러면 이점이 통째로 사라집니다. 실제로 위의 한 칸 걸러 비우기에서 버디도 똑같이 32조각이 됩니다.
**이길 조건을 안 갖춘 채로 "이 구조가 낫다"고 말하면 안 됩니다.**

**6. 이중 free 를 조용히 넘어가면 안 됩니다.** 같은 자리를 두 번 세어 남은 공간이 부풀고,
그 뒤로는 **없는 자리를 떼어줍니다.** 손상은 한참 뒤에 드러납니다.

**7. bump 는 나쁜 설계가 아닙니다.** 수명이 다 같으면 관리할 것이 없습니다(요청 단위 아레나,
컴파일러의 패스별 메모리, 게임의 프레임 메모리). **관리 비용은 수명이 제각각일 때 생깁니다.**

**8. 변종 11개 중 10개가 잡혔습니다.** 살아남은 하나는 "왼쪽부터 합치기"였는데,
확인해보니 **결함이 아니었습니다.** 인덱스를 보정하면 왼쪽부터 해도 맞습니다.
테스트를 고치는 대신 제 주석을 고쳤습니다. 보정을 빼면 그때는 잡힙니다.
