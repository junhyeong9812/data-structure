# 26. 영속 자료구조

01번부터 25번까지 만든 것은 전부 **덮어썼습니다.** `put` 을 하면 이전 상태가 사라집니다.
"5분 전 상태"를 물으면 답할 방법이 없습니다. **시간 축이 없었습니다.**

영속(persistent) 자료구조는 **바꾸지 않습니다. 새 버전을 만듭니다.**
그런데 버전마다 통째로 복사하면 수정 하나가 O(n) 이라 쓸모가 없습니다.

## 경로 복사

바뀐 길목만 새로 만들고 **나머지는 옛 버전과 공유합니다.**

```
트리에 키 하나를 넣으면
  새로 만드는 것   뿌리에서 그 자리까지의 경로. O(log n) 개
  공유하는 것      나머지 전부
```

1023개짜리 균형 트리에 키 하나를 넣으면 **새 노드 11개, 공유 1013개**입니다.
새 버전 하나가 11개짜리이고 옛 버전 1023개는 그대로 살아 있습니다.

**공유가 안전한 이유는 불변이기 때문입니다.** 아무도 안 고치니 같이 써도 됩니다.
02번 연결 리스트에서 꼬리를 공유했다면 한쪽에서 `add` 한 것이 다른 쪽에 보입니다.
불변이 먼저이고 공유는 그 결과입니다. 순서를 뒤집으면 안 됩니다.

| | 02번, 06번 | 26번 |
|---|---|---|
| `put`, `add` 의 반환형 | 옛 값 또는 void | **새 자료구조** |
| 수정 하나가 만드는 노드 | 1개 | **height + 1 개** |
| 옛 상태 | 사라진다 | **전부 남는다** |
| 스냅샷 m 개의 메모리 | O(m n) | **O(n + m log n)** |
| 조회에 잠금이 | 필요하다 | **필요 없다** |

## 값이 같은 것과 같은 객체인 것

이 박스의 계약은 **`assertEquals` 로 검증할 수 없습니다.**
`put` 이 안 지나간 부분트리를 통째로 복사하도록 고쳐도 답은 한 글자도 안 틀립니다.
그 변종은 **61개 중 56개를 통과**합니다. 갈리는 것은 참조 동일성을 보는 다섯 개뿐입니다
(`assertSame` 하나와 `countSharedNodes` 넷).

```
b = a.prepend(1) 일 때  b.tail() 이 a 와 같은 객체여야 한다
put 뒤에              안 지나간 쪽 자식이 옛 노드와 같은 객체여야 한다
```

값만 보는 테스트는 "O(n) 메모리로 O(log n) 인 척하는 구현"을 그대로 통과시킵니다.

통과하는 6개 중 셋은 빈 목록, 빈 맵, 빈 저장소라 미리 채워둔 코드만 봅니다.
나머지 셋은 "필드가 전부 final 인가", "void 를 반환하는 public 메서드가 없는가",
"synchronized 가 없는가"를 리플렉션으로 보는 **구조 테스트**입니다.
스켈레톤도 그 구조는 이미 갖췄습니다. 채우는 것은 동작이지 구조가 아닙니다.

참고: 필드 이름 `root`, `Node` 의 `key, value, left, right, size`,
`ConsList` 의 `head, tail, size` 는 테스트가 직접 들여다봅니다.

## 특히 생각해볼 것

**1. 균형을 잡지 않습니다. 그리고 그 대가가 06번보다 큽니다.**
정렬 순서로 1000개를 넣으면 06번처럼 한 줄이 됩니다. 06번에서는 그것이 O(n) 조회를 뜻했는데
여기서는 **O(n) 메모리**까지 뜻합니다. 경로가 곧 트리 전체라 `put` 하나가 노드 1001개를 만들고
**공유가 0개**입니다. 1000개를 넣는 데 노드 500,500개를 씁니다.
불변 트리의 균형은 회전을 쓸 수 없어 어렵고, 실무의 Clojure 와 Scala 는 트리 대신
**HAMT**(해시로 자리를 정하는 32갈래 트라이)를 써서 이 문제를 피합니다.

**2. 상수 인자가 큽니다. 영속이 이기는 것은 버전이 필요할 때뿐입니다.**
1023개짜리 맵을 1000번 고치면 노드를 **11,000개** 만듭니다. 가변 BST 는 잎 하나씩 **1,000개**입니다.
버전을 아무도 안 볼 것이라면 그 10,000개가 전부 GC 로 갈 쓰레기입니다. 11배가 그 값입니다.
반대로 시점 100개를 남기면 **1,100개 대 107,350개**로 97배가 뒤집힙니다.
같은 자료구조가 워크로드에 따라 11배 손해였다가 97배 이득입니다.

**3. 조회에 잠금이 필요 없습니다.** 10번 LRU 캐시, 14번 유니온파인드, 23번 스플레이 트리는
조회가 쓰기라 읽기에도 잠금이 필요했습니다. 여기서는 아무도 안 고치므로 경쟁 자체가 없습니다.
`LockFreeReadTest` 가 8개 스레드로 같은 버전을 동시에 읽고, 옆에서 쓰는 스레드가
버전 2000개를 만드는 동안에도 옛 버전의 답이 흔들리지 않는 것을 확인합니다.

**4. 없는 키를 지우면 맵 자신이 돌아옵니다.** 하위 호출이 같은 참조를 돌려주면
그 아래에서 아무것도 안 바뀐 것이므로 위에서도 새로 만들지 않습니다.
그 검사를 빼면 답은 맞고 메모리만 샙니다. `assertSame(map, map.remove(99))` 가 그것을 잡습니다.

**5. 버전 목록과 undo 이력은 다른 것입니다.** `VersionedStore` 가 목록을 둘 드는 이유입니다.
되돌린 뒤 새로 쓰면 앞으로 갈 가지는 이력에서 빠지지만 버전 목록에는 남습니다.
그래야 이미 나눠준 버전 번호가 무효가 되지 않습니다. git 의 dangling commit 과 같은 상태입니다.

## 한계 (고칠 수 없는 성질)

**1. 재귀라 깊은 트리에서 스택이 터집니다.** 이 기계 기본 스택에서 정렬 입력
**1만 200은 되고 1만 300에서 `StackOverflowError`** 입니다. 균형이 없으므로 정렬 입력의 깊이가
곧 원소 수입니다. 23번은 하향식 반복으로 피할 수 있었지만 경로 복사는 되짚어 올라오며
노드를 만들어야 해서 반복문으로 옮기기가 더 어렵습니다. 테스트가 정렬 입력을 1000개로 제한한 이유입니다.

**2. 뒤에 붙이는 연산이 없습니다.** `ConsList` 에 `append` 가 없는 것은 게을러서가 아닙니다.
마지막 노드를 고칠 수 없으므로 n 개를 전부 새로 만들어야 합니다. `reverse` 도 같은 이유로
노드 n 개를 만들고 **아무것도 공유하지 못합니다.** 불변이 공짜로 주는 것은 앞에 붙이기뿐입니다.

**3. 테스트가 못 잡는 변종이 셋 있습니다.** 19개를 돌려 16개를 잡았습니다.
못 잡은 셋은 전부 동치 변환이라 판정했습니다.

| 변종 | 왜 동치인가 |
|---|---|
| 삭제에서 후속자 대신 선행자를 쓴다 | 둘 다 옳다. 06번이 후속자를 골랐을 뿐이고 노드 수도 같다 |
| `IdentityHashMap` 대신 `HashSet` | `Node` 에 `equals` 가 없어 지금은 참조 비교다. 우연히 맞는다 |
| 공유 노드를 만나도 끝까지 내려간다 | 그 아래가 전부 공유이므로 합이 같다. 느릴 뿐이다 |

두 번째는 지우지 않고 남깁니다. 나중에 `Node` 에 `equals` 가 생기면 그날부터 틀리는데,
그 버그는 지금 있는 어떤 테스트도 잡지 못합니다.
