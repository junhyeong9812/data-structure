# 23. 스플레이 트리

06번 이진 탐색 트리가 정렬 입력에서 무너진 뒤로 균형을 잡는 방법을 셋 봤습니다.
12번은 **확률**로, 15번은 **위로 자라기**로, 16번은 **회전으로 보장**했습니다.

스플레이 트리는 **균형을 아예 목표로 삼지 않습니다.** 대신 접근한 노드를 뿌리로 끌어올립니다(splay). 그것뿐입니다.

색 비트도, 높이 필드도, 균형 조건도 없습니다. **노드에 여분 데이터가 하나도 없습니다.**
`SplayTree.Node`는 `key, value, left, right` 넷이고 `NoExtraFields` 테스트가 그걸 못 박습니다.

그런데도 **상환(amortized) O(log n)**이 나옵니다. 연산 하나는 O(n)일 수 있지만 **m번의 연산 전체가
O(m log n)**입니다. **상환 분석이 처음 나오는 자리**이고, 01번의 "2배로 키우기"와 같은 논증입니다.

그리고 공짜 기능이 따라옵니다. **최근에 쓴 것이 얕은 곳에 있습니다.** 10번 LRU 캐시가 리스트를 손으로 관리해 얻던 성질을 **구조가 저절로** 갖습니다.

| | 레드블랙(16) | 스플레이(23) |
|---|---|---|
| 노드의 여분 데이터 | 색 비트 | **없다** |
| 한 연산 최악 | **O(log n) 보장** | O(n) |
| m 연산 전체 | O(m log n) | **O(m log n) 상환** |
| 최근 쓴 것 | 상관없다 | **얕다** |
| 조회가 쓰기인가 | 아니다 | **그렇다** |

## zig-zig 의 순서가 전부입니다

zig-zig 에서 **무엇을 먼저 돌리느냐**가 갈림길입니다. "부모 먼저"로 하면 한 층씩 끌어올리는 것과
같아져(move-to-root) **답은 똑같이 나오고** 경로가 절반으로 안 접힐 뿐입니다. 1000개를 정렬 순서로 넣고 0부터 999까지 조회하면

```
할아버지 먼저(splay)        회전   5,259번
부모 먼저(move-to-root)     회전 500,499번     <- n(n-1)/2 규모
```

`MoveToRootTree`가 그 잘못된 순서를 그대로 구현해 둔 클래스입니다. 비교하려고 둡니다.

## 특히 생각해볼 것

**1. 조회가 구조를 바꿉니다.** `get(k)` 한 번이면 `depthOf(k) == 0`이고 `floorKey`도 그렇습니다.
10번 LRU의 `get`, 13번 lazy의 `rangeSum`, 14번 유니온파인드의 `find`와 같은 성질입니다. **그래서
읽기 잠금을 못 씁니다.** 읽기가 많을수록 동시성이 나빠지는, 거꾸로 선 자료구조입니다.

**2. 정렬 입력에서 죽지 않습니다. 다만 즉시 좋아지지도 않습니다.** 0..999를 순서대로 넣으면 그 순간 **높이 1000짜리 한 줄**입니다.

```
넣은 직후    높이 1000
get(0)       높이  501     회전 999번을 한 번에 쓴다
get(999)     높이  502
get(500)     높이  252
```

16번은 넣는 내내 높이가 20을 안 넘었습니다. **보장받는 것과 사후에 접히는 것의 차이**입니다.

**3. zig-zig 순서를 바꿔도 계약 테스트는 전부 통과합니다.** 변종으로 확인했더니 **34개 중 29개가
통과합니다.** 탐색 성질도 TreeMap 2만 스텝 대조도 green이고 갈리는 것은 `AmortizedCostTest`
다섯 개뿐입니다. **고칠 수 없는 성질은 답이 아니라 걸음 수로만 잡힙니다.**

**4. 최근 접근이 몰리면 빠릅니다.** 10만 개 중 100개만 100번씩 돌아가며 조회하면

```
스플레이 트리   방문 노드  59,653   조회당  5.96
완전 균형 BST   방문 노드 159,800   조회당 15.98
```

**5.96은 log2(100,000) = 16.6이 아니라 log2(100) = 6.64 근처**입니다. 비용이 트리의 크기가 아니라
**최근에 쓴 것의 개수**로 정해집니다. 비교 상대가 레드블랙이 아니라 **완전 균형 BST**인 것은
16번 파일에 계수기를 넣지 않았기 때문인데, 16번이 도달할 수 있는 최선이라 더 센 비교입니다.

**5. `remove`가 splay를 두 번 부릅니다.** 06번처럼 후속자를 찾아 옮겨 심지 않습니다.

## 한계 (고칠 수 없는 성질)

**1. 단일 연산 최악은 O(n)입니다.** 2000개를 정렬 순서로 넣고 `get(0)`을 부르면 노드 2000개를 지나고
회전 1999번을 합니다. 16번이 21을 보장하던 자리입니다. **보장이 아니라 상환입니다.**

**2. 재귀 구현이라 깊은 트리에서 스택이 터집니다.** 이 기계 기본 스택에서 정렬 입력 **1만 4천은 되고
1만 6천에서 `StackOverflowError`**입니다. 성능 테스트가 20만 개를 **섞어서** 넣는 이유이고,
실무 구현이 하향식(top-down) 반복 splay를 쓰는 이유이기도 합니다.

**3. 테스트가 못 잡는 변종이 하나 있습니다.** `SplayTreeSet.add`가 `contains`로 먼저 확인하게 바꿔도
**34개가 다 통과합니다.** 답도 회전 수도 같고 방문 노드만 두 배가 됩니다.
(11번 `h2 == 0`, 16번 뿌리 색, 18번, 22번 패딩 채우기에 이어 **다섯 번째**입니다.)

**4. `SortedTree` 인터페이스만 보면 16번과 구별할 수 없습니다.**
같은 계약 뒤에 "조회가 쓰기인 구현"이 앉아 있어도 **타입이 그 차이를 말해주지 않습니다.**
