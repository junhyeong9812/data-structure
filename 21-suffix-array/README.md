# 21. 접미사 배열

09번 마지막 문제가 "서로 다른 부분 문자열 수"였습니다. 접미사를 전부 트라이에 밀어 넣고
만들어진 노드를 세면 답이 나왔습니다. 답은 맞습니다. **노드가 O(n^2)입니다.**

길이 1000이면 노드 50만 개, 길이 10만이면 **50억 개**입니다. 노드 하나를 40바이트로 쳐도 200GB입니다.
09번 문서에 "접미사 배열과 접미사 오토마타가 존재하는 이유"라고 적고 넘어갔습니다. 그 약속을 여기서 갚습니다.

## 접미사를 저장하지 않습니다

```
0 banana                5 a
1 anana    사전순 정렬   3 ana
2 nana        ->        1 anana
3 ana                   0 banana
4 na                    4 na
5 a                     2 nana
```

남는 것은 **오른쪽 열의 숫자 6개**입니다. 문자열은 하나도 새로 만들지 않습니다. O(n) 공간의 정체입니다.

| 길이 1000 | 09번 접미사 트라이 | 접미사 배열 |
|---|---|---|
| 저장 단위 | 노드 **500,500개** | int **1,000개** |
| 길이 10만이면 | 노드 5,000,050,000개 | **400,000바이트** |

## 여기에 LCP를 얹으면 뺄셈이 됩니다

LCP 배열은 **이웃한 두 접미사가 앞에서 몇 글자까지 같은가**입니다. banana면 `[0, 1, 3, 0, 0, 2]`입니다.

```
서로 다른 부분 문자열 수 = n(n+1)/2 - sum(lcp)
가장 긴 반복 부분 문자열   = lcp의 최댓값
```

접미사 하나가 부분 문자열 (길이)개를 만듭니다. 다 더하면 `n(n+1)/2`이고, 정렬해 두면
**겹쳐서 센 것이 바로 앞 이웃과의 공통 접두사뿐**이라 한 번씩만 빼면 됩니다.
09번은 길이 1000이 한계였는데 여기서는 10만도 되고, 답이 49억이라 **int로는 담기지도 않습니다.**

## 대가

**직관을 버립니다.** 트라이는 car와 card가 c-a-r을 공유하는 그림이 그려집니다.
접미사 배열은 안 그려집니다. 숫자 배열 두 개를 보고 "이게 그 뜻이다"라고 믿어야 합니다.

| | 트라이(09번) | 접미사 배열 |
|---|---|---|
| 부분 문자열 찾기 | O(m), 대신 접미사를 다 넣어야 한다 | **O(m log n)** |
| 공간 | 접미사를 넣으면 O(n^2) | **O(n)** |
| 만드는 비용 | 넣으면서 자동 | **O(n log^2 n) 선행 계산** |

트라이는 한 글자에 한 걸음입니다. 접미사 배열은 **이진 탐색이라 log n번 찔러봅니다.**
길이 10만에서 33번이고 `searchIsLogarithmic` 테스트가 그 값을 셉니다.

## 특히 생각해볼 것

**1. 배가법이 재활용하는 것은 "순위"입니다.** 1글자 순위를 매기고 `(내 순위, k칸 뒤 순위)`로 정렬하면
**2k 글자까지 비교한 셈**이 됩니다. 순위가 이미 k 글자를 요약하고 있기 때문입니다.
그래서 정렬을 log n번만 하면 되고 비교는 정수 두 개 비교라 상수입니다.

**2. `reRank`가 이 문제의 핵심입니다.** 정렬한 뒤 **같은 쌍끼리 같은 순위로 묶어야** 합니다.
그냥 `i`를 넣으면 같은 것이 다른 순위를 받고 다음 라운드가 통째로 틀어집니다.
변종으로 심어봤더니 90개 중 **35개**가 무너졌습니다.

**3. 범위 밖을 -1로 봐야 합니다.** `rank[i+k]`에서 `i+k`가 문자열을 넘으면 0이 아니라 **-1**입니다.
0으로 두면 "문자열이 끝났다"와 "순위가 0인 접미사가 이어진다"가 같아집니다.
`a`가 `ab`보다 앞인 이유가 이것입니다. 이걸 0으로 바꾸면 22개가 무너집니다.

**4. Kasai가 O(n)인 이유는 훑는 순서에 있습니다.** 순위 순서가 아니라 **원문 순서로** 갑니다.
그러면 위치 i의 LCP가 h였을 때 **위치 i+1의 LCP는 최소 h-1**입니다. 앞 글자 하나만 떨어져 나갔으니까요.
0으로 되돌리지 않고 1만 빼고 이어서 셉니다. h는 최대 n번 늘고 n번 줄어 합이 O(n)입니다.
같은 글자 2000개에서 **결과값의 합은 1,999,000인데 Kasai가 훑는 글자는 1,999개**입니다.
매번 0부터 세게 바꾸면 답은 같고 비용만 O(n^2)가 되는데, `Amortized` 테스트가 그것을 잡습니다.

**5. 검색은 이진 탐색 두 번이고 한 글자 다릅니다.** `< 0`이냐 `<= 0`이냐이고,
**`upperBound`에서 `< 0`을 쓰면 두 경계가 같아져 개수가 늘 0**이 됩니다.
찾은 위치를 그대로 주면 안 됩니다. 사전순이라 banana에서 `a`를 찾으면 5, 3, 1 순으로 나옵니다.

**6. 문제 3의 구분자.** `a = "a"`, `b = "aa"`를 그냥 이으면 `"aaa"`가 되고
경계를 넘는 쌍이 `"aa"`를 공통이라고 보고합니다. **`a`에는 `"aa"`가 없습니다.**
구분자를 빼면 5개가 무너집니다. 그래서 **입력에 구분자가 있으면 거부해야 합니다.**

**7. 테스트가 구별하지 못하는 코드가 셋 있습니다.** 정직하게 적어둡니다.

- **Kasai의 `h = 0` 되돌리기.** `rank[i] == 0`인 자리에서 **h는 이미 0입니다.** 거기 오는 접미사가
  사전순 최소인데 h >= 1이면 자기보다 작은 접미사가 있다는 뜻이라 모순입니다. 지워도 90개가 다 통과합니다.
- **`reRank`의 `< 0`을 `!= 0`으로.** 이미 정렬한 뒤라 앞 것이 뒤 것보다 클 수 없습니다. 동치입니다.
- **문제 3에서 구분자 접미사를 거르는 검사.** 구분자로 시작하는 접미사가 하나뿐이라
  이웃과의 LCP가 늘 0입니다. 최댓값이 될 수 없어 걸러도 안 걸러도 답이 같습니다.

11번 `h2 == 0`, 16번 "뿌리를 빨갛게", 18번 `nextSetBit`의 범위 검사에 이어 같은 계열입니다.
**불변식을 지키는 코드가 여럿이면 그중 하나가 나머지를 여벌로 만듭니다.**
종료 조건도 그렇습니다. "순위가 전부 갈렸는가" 대신 `k >= n`까지 돌려도 답은 같고,
90개 중 라운드 수를 세는 4개만 무너집니다.

## 한계

- **만들어야 씁니다.** 문자열이 바뀌면 **처음부터 다시 만듭니다.** 갱신이 잦으면 맞지 않습니다.
- **O(n log^2 n)입니다.** 기수 정렬이면 O(n log n), SA-IS면 O(n)까지 갑니다.
  게다가 `int[]`는 Comparator로 정렬할 수 없어 **`Integer[]`로 박싱**합니다. 상수가 큽니다.
- 검색이 **O(m log n)**입니다. O(m)로 돌아가려면 LCP를 얹은 이진 탐색이나 접미사 오토마타가 필요합니다.
